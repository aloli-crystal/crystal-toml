Parser et sérialiseur TOML v1.0 pour Crystal, avec **préservation
des commentaires et de la mise en forme** lors d'un round-trip
`parse → modification → écriture`. Crystal pur, aucune dépendance
runtime.

**Conformité totale (100 %)** avec la suite officielle d'interop
https://github.com/toml-lang/toml-test[`toml-lang/toml-test`] v2.1.0
(205/205 tests valid, 473/473 tests invalid).

Documentation API : https://aloli-crystal.github.io/crystal-toml/

toc::[]

== Pourquoi crystal-toml

L'écosystème Crystal compte déjà une bibliothèque TOML,
https://github.com/crystal-community/TOML.cr[`crystal-community/TOML.cr`].
Elle fonctionne, mais a trois limites bloquantes pour les usages
visés par ce shard :

. **Parsing uniquement.** Aucun moyen d'écrire du TOML
  programmatiquement.
. **TOML v0.5.0** — la spec a été stabilisée en v1.0.0 en 2021.
  Les deltas (inline tables multi-lignes, dotted keys, `inf` /
  `nan`, formes datetime modernes) ne sont pas pris en compte.
. **Sortie en `Hash` plat.** Commentaires, lignes vides et ordre
  de déclaration sont perdus. Impossible de lire une config,
  modifier une valeur et la réécrire sans diffuser tout le
  fichier.

`crystal-toml` est bâti autour de trois objectifs :

. **Conformité TOML v1.0**, validée contre la suite officielle
  `toml-lang/toml-test` (le seul harnais d'interop faisant
  autorité). 100 % à chaque release.
. **Round-trip byte-identique** : `TOML.parse(s).to_toml == s`
  pour tout `s` valide. L'AST garde les trivia (commentaires,
  espaces, lignes vides, formatage original des nombres et
  chaînes) attachés à ses nœuds.
. **Modifications ciblées** qui ne touchent qu'à ce que vous
  changez. Modifiez une valeur dans une config de 200 lignes et
  le diff fait une ligne, pas tout le fichier reformaté.

Le shard alimente `crystal-secrets` chez Aloli, où des coffres
TOML sont versionnés dans git, annotés avec des commentaires
(`# rotation 2026-04-15`) et édités programmatiquement sans
perdre ces annotations.

== Installation

Ajoutez la dépendance à votre `shard.yml` :

[source,yaml]
----
dependencies:
  crystal-toml:
    github: aloli-crystal/crystal-toml
    version: "~> 0.1"
----

Puis `shards install`.

Crystal ≥ 1.19.0. Aucune dépendance runtime.

== Démarrage rapide

Deux surfaces d'API selon ce que vous voulez faire.

=== Mode drop-in — `TOML.parse_to_hash`

Pour les consommateurs en lecture seule — rapide, `Hash` plat,
perd tous les commentaires et le formatage original. Compatible
drop-in avec `crystal-community/TOML.cr`.

[source,crystal]
----
require "crystal-toml"

source = File.read("config.toml")
config = TOML.parse_to_hash(source)

puts config["title"]
puts config["server"].as(Hash(String, TOML::Type))["host"]
----

`TOML.parse_to_hash` retourne `Hash(String, TOML::Type)` où
`TOML::Type` est l'union récursive :

[source,crystal]
----
alias TOML::Type = Nil | String | Int64 | Float64 | Bool |
                   Time | Time::Span |
                   Array(TOML::Type) | Hash(String, TOML::Type)
----

=== Mode préservation — `TOML.parse`

Pour ceux qui écrivent ou round-trippent — retourne un AST
`TOML::Document` qui garde commentaires, lignes vides, ordre des
clés et formatage byte-level d'origine :

[source,crystal]
----
require "crystal-toml"

doc = TOML.parse(File.read("vault.toml"))

# Lecture avec accesseurs typés
db_url = doc.string("DATABASE_URL")
port   = doc.int?("server.port") || 8080

# Modification
doc.set("DATABASE_URL", "postgres://new...")
doc.set_with_comment("API_KEY", "ak_...", "rotated 2026-04-28")
doc.delete("OLD_TOKEN")

# Réécriture — commentaires, blancs et formatage de chaque ligne
# non touchée préservés byte-pour-byte.
File.write("vault.toml", doc.to_toml)
----

== Lecture des valeurs

`Document` expose des accesseurs typés pour chaque type scalaire
TOML. Chacun en deux formes :

* **`#TYPE?(path)`** — retourne la valeur si elle existe *et*
  matche le type demandé, `nil` sinon.
* **`#TYPE(path)`**  — pareil, mais lève `KeyError` si absente
  ou `TypeCastError` si mauvais type.

[source,crystal]
----
doc = TOML.parse(<<-TOML)
  title = "Exemple"
  port  = 8080
  pi    = 3.14
  on    = true
  when  = 1979-05-27T07:32:00Z
  dur   = 07:32:00

  [server]
  host = "0.0.0.0"
  TOML

doc.string("title")           # => "Exemple"
doc.int("port")               # => 8080_i64
doc.float("pi")               # => 3.14
doc.bool("on")                # => true
doc.datetime("when").year     # => 1979
doc.time_of_day("dur")        # => 07:32:00.0 (Time::Span)
doc.string("server.host")     # => "0.0.0.0"

doc.has_key?("server.host")   # => true
doc.has_key?("server.tls")    # => false
doc.string?("missing")        # => nil
doc.int?("title")             # => nil  (mauvais type, sans raise)

doc.string("title.x")         # lève KeyError
doc.string("port")            # lève TypeCastError
----

Le path est une string pointée. Pour des clés contenant
elles-mêmes un point, utilisez la forme `Array(String)` :

[source,crystal]
----
doc = TOML.parse(%("a.b" = 1))
doc.get?(["a.b"])             # => 1_i64
----

`#get?(path)` et `#get(path)` retournent la valeur `TOML::Type`
brute sans filtrage de type quand vous voulez gérer le type
vous-même.

== Édition de valeurs

Les clés top-level peuvent être remplacées, insérées ou
supprimées en préservant la mise en forme de toutes les autres
lignes :

[source,crystal]
----
doc = TOML.parse(<<-TOML)
    name   = "old"   # original
    port   = 8080

    [server]
    host = "0.0.0.0"
    TOML

# Remplacement : whitespace autour et commentaire trailing
# conservés.
doc.set("name", "new")
# →   name   = 'new'   # original

# Insertion : une nouvelle ligne est ajoutée juste après le
# dernier KV top-level, c'est-à-dire avant tout [section]. La
# nouvelle ligne utilise des literal-strings (`'...'`) si possible,
# sinon des basic strings (`"..."`) avec échappement correct.
doc.set("region", "eu-west")
# →   region = 'eu-west'

# Insertion avec commentaire :
doc.set_with_comment("API_KEY", "ak_xxx", "rotation 2026-04-28")
# →   API_KEY = 'ak_xxx' # rotation 2026-04-28

# Suppression : retourne true si une ligne a été retirée, false
# sinon.
doc.delete("port")            # => true
doc.delete("nope")            # => false
----

`#set` est surchargée pour `String`, `Int`, `Float`, `Bool`. Les
floats émettent automatiquement `inf` / `-inf` / `nan` pour les
valeurs non finies correspondantes.

[NOTE]
====
**Limitation v0.1** : l'édition opère sur **les clés top-level
uniquement**. Modifier une valeur dans un bloc `[section]` ou via
un path pointé n'est pas encore supporté dans cette release. Pour
ces cas, reconstruisez le document manuellement ou attendez la
v0.2.
====

== Préservation au round-trip

La fonctionnalité phare : un document parsé peut être
re-sérialisé byte-pour-byte à l'identique, même si l'input est
plein de commentaires, lignes vides et mises en forme inhabituelles :

[source,crystal]
----
src = <<-TOML
  # Coffre des secrets de prod
  # Rotation trimestrielle — dernière mise à jour 2026-04-15

  DATABASE_URL = "postgres://prod/db"
  API_KEY      = "ak_xxx"        # ne jamais logger !

  [stripe]
  # Clés live — manipuler avec précaution
  secret_key      = "sk_live_..."
  webhook_secret  = "whsec_..."
  TOML

doc = TOML.parse(src)
doc.to_toml == src   # => true (byte-identique)
----

Après modification, seules les lignes touchées changent. Tous les
autres bytes de l'original sont préservés :

[source,crystal]
----
doc.set("DATABASE_URL", "postgres://prod/new")
new_src = doc.to_toml
# Diff vs src : exactement une ligne changée (DATABASE_URL),
# chaque commentaire, ligne vide et KV adjacent byte-identique.
----

Cela rend `crystal-toml` adapté à de l'outillage qui édite des
fichiers TOML écrits par des humains (configs CI, coffres de
secrets, manifestes de projet) sans introduire de churn dans les
diffs en versionning.

== Types TOML → types Crystal

[cols="3,3",options="header"]
|===
| Type TOML 1.0 | Type Crystal retourné

| Basic / multi-line basic / literal / multi-line literal string
| `String` (escapes décodés)

| Integer décimal / hex / octal / binaire
| `Int64`

| Float (avec exposant / `inf` / `nan`)
| `Float64`

| Boolean
| `Bool`

| Offset datetime (RFC 3339 avec timezone)
| `Time` (avec la `Time::Location` appropriée)

| Local datetime (sans timezone)
| `Time` en location UTC

| Local date
| `Time` à minuit UTC

| Local time
| `Time::Span` depuis minuit

| Array
| `Array(TOML::Type)` (récursif)

| Inline table ou `[section]`
| `Hash(String, TOML::Type)` (récursif)

| Array of tables `[[…]]`
| `Array(Hash(String, TOML::Type))`
|===

En **mode préservation** (`TOML.parse`), chaque valeur est
encapsulée dans une sous-classe typée `TOML::Value` qui porte
aussi le texte source `raw` original. Les quatre variantes
datetime sont gardées distinctes (`OffsetDateTimeValue`,
`LocalDateTimeValue`, `LocalDateValue`, `LocalTimeValue`) pour
qu'un round-trip préserve la forme exacte écrite par l'auteur.

== Migration depuis crystal-community/TOML.cr

Si votre code utilise `crystal-community/TOML.cr` :

[source,crystal]
----
# Avant
require "toml"

hash = TOML.parse(File.read("config.toml"))
----

La migration est un changement d'une ligne dans `shard.yml` :

[source,yaml]
----
dependencies:
  crystal-toml:                  # avant: toml
    github: aloli-crystal/crystal-toml
    version: "~> 0.1"
----

Et un changement de nom de méthode dans votre code :

[source,crystal]
----
require "crystal-toml"

hash = TOML.parse_to_hash(File.read("config.toml"))
----

Le `Hash(String, TOML::Type)` retourné est équivalent en
structure. L'alias `TOML::Type` est plus large (il ajoute
`Time::Span` pour les local times) mais se comporte par ailleurs
de la même façon.

Si vous avez besoin de relire votre config en Crystal *et* de
l'éditer plus tard, basculez sur `TOML.parse` et utilisez l'API
AST décrite plus haut.

== Limitations (v0.1)

* **Édition top-level uniquement.** `Document#set` / `#delete` /
  `#set_with_comment` opèrent sur les bare keys top-level.
  Modifier une valeur dans un `[section]` ou via un path pointé
  n'est pas encore supporté dans cette release.
* **Pas de validation de schéma.** Le shard valide la *syntaxe*
  TOML, pas vos sémantiques métier.
* **Pas de streaming.** Le document complet est lu en mémoire et
  décodé en AST. Les fichiers de l'ordre du Mo passent sans
  problème ; les fichiers de l'ordre du Go ne sont pas la cible.
* **Pas d'encoder pour toml-test.** Le shard livre
  `bin/crystal-toml-decoder` (TOML → JSON) mais pas l'encoder TOML
  correspondant. Le round-trip de parsing est entièrement validé,
  mais le côté encoder JSON-driven du harnais toml-test est laissé
  pour une version ultérieure.

Ces points sont suivis pour la v0.2+.

== Architecture

Le pipeline est un classique en trois phases :

----
                Lexer            Parser              Document
String  ──────► tokens  ───────► nœuds AST  ───────► Hash<String, Type>
              + trivia          + raw text          (parse_to_hash)
                                  sur chaque nœud
                                       │
                                       └──► to_toml ──► String byte-identique
----

* **Lexer** (`src/toml/lexer.cr`) : streaming, émet les tokens
  trivia plutôt que de les ignorer. UTF-8 validé en amont.
* **Parser** (`src/toml/parser.cr`) : descente récursive sur le
  flux de tokens. Replie les trivia dans les champs raw des nœuds
  environnants pour que le serializer puisse re-émettre
  byte-pour-byte.
* **AST** (`src/toml/node.cr`, `src/toml/value.cr`) : liste plate
  des lignes top-level (`KeyValueLine`, `TableHeaderLine`,
  `ArrayOfTablesLine`, `CommentLine`, `BlankLine`). Chaque nœud
  stocke assez de texte source verbatim pour être re-émis sans
  changement.
* **HashBuilder** (`src/toml/hash_builder.cr`) : parcourt l'AST et
  produit la sortie `Hash(String, Type)` plate. Applique aussi
  toutes les règles sémantiques de la spec (clés dupliquées,
  redéfinitions de tables, fermeture des inline tables, conflits
  dotted-key, etc.).

Un module séparé `TestFormat` (`src/toml/test_format.cr`)
parcourt l'AST et émet la forme JSON attendue par `toml-test`,
utilisée uniquement par le binaire decoder.
